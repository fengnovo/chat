**当前项目已经有相当完整的生产架构基础，下一步最值得投入的是“收紧运行时边界、补齐故障验证、消除权限例外”，然后再做模块重构。** 我建议保留 PostgreSQL、BullMQ、LangGraph 和现有执行租约机制，逐步整理核心，而不是整体换成 Pi。

这次对比读取了当前项目的 API、Worker、agent-core、数据库实现、CI 和相关测试；Pi 固定在提交 `1cedd327`，本地最终检查在 `dc22fc8`。没有修改项目代码。

先校准比较基准：Pi durable 的 README 明确标为 **Experimental**，并且说明一个 storage 同时由一个进程拥有，没有跨进程锁。它是很有参考价值的运行时设计，但不能直接作为分布式、多租户平台的完整生产标准。[Pi README](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/README.md)

两者的核心差异如下：

| 维度 | Pi durable | 当前项目 | 我的判断 |
|---|---|---|---|
| 产品范围 | 会话、任务、文档运行时库 | 多客户端、多租户、沙箱、知识库平台 | 当前系统承担更多生产责任 |
| 持久化组织 | entries、tasks、documents 通过统一 commit 提交 | Run、事件、工具账本、子任务、LangGraph checkpoint 分层持久化 | 你需要明确各层一致性规则 |
| 多 Worker 并发 | storage 单进程拥有 | PostgreSQL lease、token、epoch、fenced checkpoint | 现有设计应保留 |
| 工具故障恢复 | durable intent；恢复时严格检查 replay policy | 已有工具账本、结果复用、uncertain、重复执行审批 | 基础完整，策略还可收紧 |
| 升级兼容 | task/document version、迁移、不兼容时阻塞 | 有数据库迁移、legacy guard、工具结果 codec v1 | 缺少完整的运行版本兼容策略 |
| 状态订阅 | 提交后发布；慢消费者可以重新获取快照 | 持久化事件、Redis 通知、SSE 重放 | 长历史读取和背压需要完善 |
| 测试组织 | 存储一致性套件、分阶段恢复测试、benchmark | 已有单测、DB 集成测试、SIGKILL 测试 | 最关键的恢复测试没有进入默认 CI |

这里尤其要肯定你已经做对的部分：`withLease()` 使用行锁、token/epoch 和事务前后 TTL 检查；checkpoint 写入与 ownership 校验使用同一数据库事务；终态事件与 Run 状态一起提交；事件先落库再通知 Redis。这些都是值得继续维护的基础。[执行租约](/Users/keen/Desktop/code/projects/chat/packages/db/src/durable-execution.ts:97)、[checkpoint fencing](/Users/keen/Desktop/code/projects/chat/apps/worker/src/fenced-checkpointer.ts:17)、[终态提交](/Users/keen/Desktop/code/projects/chat/packages/db/src/durable-execution.ts:258)

1. **P0：先修复权限边界中的例外路径。**

   预览接口在全局 hook 中直接跳过鉴权，随后仅依赖 `Origin/Referer` 判断来源，再通过没有租户条件的 session 查询定位工作区。知道会话标识的请求，可以绕开正常的用户访问控制；HTTP 客户端也可以自行设置这些来源头。[跳过鉴权](/Users/keen/Desktop/code/projects/chat/apps/api/src/app.ts:139)、[预览处理](/Users/keen/Desktop/code/projects/chat/apps/api/src/routes.ts:1217)、[无租户查询](/Users/keen/Desktop/code/projects/chat/packages/db/src/repository.ts:1098)

   预览文件读取还存在另一个边界问题：`path.resolve()` 加 `startsWith()` 只检查路径字符串，随后 `stat/readFile` 会跟随符号链接。我用临时合成文件复现了“检查通过，但读取到预览目录之外的文件”。[文件读取逻辑](/Users/keen/Desktop/code/projects/chat/apps/api/src/routes.ts:1248)

   建议把预览提取为独立服务边界：先校验用户对会话的权限，再签发限定资源、有效期的预览凭证；预览内容通过隔离的产物存储提供。若继续直接读取工作区，需要处理真实路径、符号链接和检查后文件变化的问题。

   另外，`createRun()` 的幂等命中只检查 `tenant_id + idempotency_key`，直接返回旧 Run，没有核对用户、会话和请求内容。我调用真实方法、使用模拟数据库结果，确认用户 A 的请求可以返回同租户用户 B 的 `userMessage`。触发前提是 key 相同。[幂等查询](/Users/keen/Desktop/code/projects/chat/packages/db/src/repository.ts:860)

   **建议将幂等身份限定到用户和会话，并保存请求摘要；同 key、不同内容返回明确冲突。** 验收应覆盖同租户不同用户、同用户不同会话、相同 key 不同输入。

2. **P0：让已有的崩溃恢复测试成为发布门槛。**

   你已经写了比较有价值的 SIGKILL 测试，包括“外部副作用完成后崩溃”和“账本成功后崩溃”。但它们受 `RUN_INTEGRATION_TESTS=1` 控制；当前 CI 只运行默认 `pnpm test`。根目录 `test:integration` 又只执行 `@repo/db`，漏掉 agent-core 的 crash E2E 和 Worker 的 fenced-checkpointer 测试。[CI](/Users/keen/Desktop/code/projects/chat/.github/workflows/ci.yml:45)、[崩溃测试](/Users/keen/Desktop/code/projects/chat/packages/agent-core/test/durable-crash.e2e.test.ts:175)、[根脚本](/Users/keen/Desktop/code/projects/chat/package.json)

   这意味着：**最能证明 durable 正确性的测试存在，但 CI 通过不能证明这些测试通过。**

   建议增加独立 PostgreSQL/Redis 集成测试任务，强制执行三个包的相关测试，并禁止关键用例静默跳过。再逐步覆盖租约交接、Redis 任务丢失、取消与完成竞争、重复审批、旧版本 checkpoint 恢复。

   Pi 值得借鉴的是把保证写成可复用的测试契约，例如“混合写入必须全部成功或全部回滚”，而不只是增加零散测试数量。[Pi 存储一致性测试](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/testing/storage-conformance.ts#L94)

3. **P1：明确一个执行内核，集中管理状态转换和提交规则。**

   现在执行规则分布在 `processor.ts`、`durable-execution.ts`、`deep-agent.ts`、`tool-execution.ts`、`durable-child.ts` 中。分文件本身没有问题，主要成本是：理解一次恢复，需要同时追踪业务 Run、图 checkpoint、工具账本、事件和子任务。

   Pi 的优势在于核心规则统一：一次 commit 可以包含任务、记录和文档；持久化成功后才发布；提交结果不确定时停止使用当前 Session。[Pi 提交实现](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/session/session.ts#L405)

   当前项目可以围绕 `claim / resume / interrupt / cancel / complete` 建立明确的应用层入口，每个入口定义：允许的前置状态、原子更新内容、可重试行为、恢复方式。跨事务的步骤则明确使用 Outbox 或对账。

   一个具体例子是：现在先提交 `run.completed`，再单独创建 memory job，并吞掉失败。如果进程死在中间，Run 已完成，记忆任务可能没有被创建。[完成后的记忆投递](/Users/keen/Desktop/code/projects/chat/apps/worker/src/processor.ts:127)

   如果长期记忆整理属于应当最终完成的能力，就应把“创建任务意图”放进终态事务，或增加补偿扫描；如果允许丢失，也应明确这种产品语义。

4. **P1：补上“部署新版本后，旧任务怎么恢复”的协议。**

   当前恢复会重新创建 runtime，使用当前配置的模型、MCP、工具策略和资源文件。已有 `legacy_execution` 和结果 codec v1 是保护，但还没有形成完整的运行版本兼容层。[runtime 重建](/Users/keen/Desktop/code/projects/chat/apps/worker/src/processor.ts:396)、[资源重新加载](/Users/keen/Desktop/code/projects/chat/apps/worker/src/processor.ts:742)

   典型场景是：任务停在工具审批处，期间升级了工具 schema 或 graph，用户第二天批准，新代码继续解释旧 checkpoint。

   建议为 Run 保存不含秘密的执行描述：runtime/graph 版本、工具 schema 或配置摘要、prompt/skills 版本，以及影响恢复语义的模型设置。恢复时明确选择“兼容执行、迁移、交给旧版本 Worker、阻塞待处理”。

   Pi 已经有 task version 和迁移检查；定义缺失、代码版本过旧、迁移失败都有明确的阻塞原因。这种显式行为很值得借鉴。[Pi 版本解析](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/harness/scheduler.ts#L826)

   **验收应包含真正的跨版本恢复测试，而不只是同版本重启。**

5. **P1：将正常工具授权与“不确定结果后的重复执行”分开。**

   当前工具账本已经能复用成功结果，也能将未知外部结果标成 `uncertain`。但当前有两处策略值得收紧：MCP 的 `readOnlyHint/idempotentHint` 可以影响自动重放判断；会话 `autoApproveTools` 会跳过 unsafe 重放审批。[重放判断](/Users/keen/Desktop/code/projects/chat/packages/agent-core/src/tool-execution.ts:163)

   后者是当前代码明确支持的行为，不是偶发 bug。但“本会话允许执行工具”和“上次可能已成功，允许再次产生副作用”是两种不同授权，涉及发消息、创建资源等操作时尤其明显。

   建议定义独立的 `uncertainOutcomePolicy`，支持查询外部结果、使用服务端幂等键、人工确认或停止执行。第三方 hint 可以作为参考，自动重放能力由可信工具配置确认。

   Pi 对恢复采取较保守的规则：**历史记录和当前工具声明都为 safe 才重跑**，否则返回 interrupted。它也没有承诺任意外部副作用的 exactly-once。[Pi 工具恢复](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/harness/tool.ts#L85)

6. **P1：为历史、推流和事件存储建立明确的资源上限。**

   当前历史接口会查询一个 session 的全部 Run，然后并发读取每个 Run 最多 100,000 条事件，在请求中重新拼接消息。`listSessionRuns()` 本身没有分页。[历史读取](/Users/keen/Desktop/code/projects/chat/apps/api/src/routes.ts:440)、[Run 列表](/Users/keen/Desktop/code/projects/chat/packages/db/src/repository.ts:836)

   同时，SSE 写入没有处理 `reply.raw.write()` 返回 `false` 的情况；慢客户端可能积累发送缓冲。Worker 对每个产生的事件分别持久化，文本碎片越多，数据库事务和行更新越多。[推流](/Users/keen/Desktop/code/projects/chat/apps/api/src/chat-stream.ts:193)、[事件消费](/Users/keen/Desktop/code/projects/chat/apps/worker/src/processor.ts:819)

   建议建立可重建的消息读取模型，历史按消息分页；实时恢复使用稳定 cursor 和 snapshot；SSE 处理背压并限制单连接缓冲。对文本增量可以按小时间窗或字节量合并，但仍保持“落库后再展示”，并在终态前 flush。

   Pi 对落后的订阅者会使用快照替换积压更新，并为工具输出设置字节、行数限制。这里值得借鉴的是**超过预算之后仍有定义明确的行为**。[Pi 事件订阅](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/harness/events.ts#L137)、[输出限制](https://github.com/earendil-works/pi/blob/1cedd32724abfcb0915f76cc61b6827e2c16dbad/packages/durable/src/harness/output.ts#L4)

7. **P2：按变化原因拆分 agent-core，隔离框架适配和产品策略。**

   `deep-agent.ts` 现在同时负责模型装配、MCP、长期记忆工具、预览工具、中文产品提示词、审批、流转换和恢复。新增一个产品能力，也需要进入运行时核心。[装配与业务工具](/Users/keen/Desktop/code/projects/chat/packages/agent-core/src/deep-agent.ts:557)

## 通俗解释当前项目里的具体代码，以及应该改什么
先记住几个角色：

- **客人**＝登录用户。
- **机器人**＝Worker 和 Agent。
- **做一个玩具**＝执行一次 Run。
- **本子**＝数据库里的执行状态、事件、工具记录和 checkpoint。
- **停电**＝进程崩溃、服务重启或者网络中断。

| 刚才的比喻 | 对应当前项目里的问题 | 应该怎么改 |
|---|---|---|
| **① 柜子的钥匙没检查好** | 预览接口跳过登录检查；创建 Run 时，相同幂等 key 可能返回同租户另一用户的记录；预览读取可能跟随符号链接读到目录外 | 每条访问路径检查用户与资源归属；幂等 key 限定用户和会话；限制预览文件的真实访问范围 |
| **② 没有参加停电考试** | 已经写了崩溃恢复测试，但默认 CI 没启用它们 | 发布前自动启动测试数据库和 Redis，强制运行这些测试 |
| **③ 几本本子没一起记** | Run 完成先保存，记忆整理任务随后才创建；中间崩溃可能漏掉后续任务 | 把必须一起保存的状态和任务意图放进同一事务，或者增加补偿扫描 |
| **④ 新说明书接不上旧玩具** | 恢复旧任务时，会用当前版本重新创建 Agent；旧 checkpoint 不一定兼容新工具、新 graph | 保存运行版本和配置摘要；恢复前检查兼容性，必要时迁移或暂停 |
| **⑤ 玩具可能送了两次** | 工具已经产生效果，但成功结果没存下来；恢复后可能重复执行。会话自动批准还会跳过 unsafe 重放审批 | 单独定义“不确定结果如何处理”；优先查结果、使用幂等键，必要时确认 |
| **⑥ 搬整座图书馆、不断塞纸** | 历史接口读取整个会话的大量事件；SSE 没有处理客户端接收太慢的背压 | 历史分页、保存可重建的消息视图；限制发送缓冲，慢客户端按游标恢复 |
| **⑦ 一个机器人干太多工作** | `deep-agent.ts` 同时负责业务提示词、工具装配、流转换和恢复 | 将产品能力、框架适配、执行恢复、展示转换分开 |
| **⑧ 大小机器人交接不清楚** | 子任务已经持久化，但后台任务主要仍跟随父 Run 的执行和取消流程 | 明确父任务结束、取消、恢复时，子任务应该如何变化；需要独立后台任务时再扩展模型 |

把前面三个最具体的问题打开，你就能直接看到对应关系：

**① “钥匙问题”对应这些位置。**

[app.ts:139](/Users/keen/Desktop/code/projects/chat/apps/api/src/app.ts:139) 对预览请求直接跳过鉴权。[repository.ts:860](/Users/keen/Desktop/code/projects/chat/packages/db/src/repository.ts:860) 找到相同租户、相同幂等 key 的旧 Run 后，直接返回，没有继续核对用户和会话。
