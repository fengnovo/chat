## 关键步骤拆解

**1. 前端发起**（[chat-runtime.tsx#L328](file:///Users/keen/Desktop/code/projects/chat/apps/web/app/components/resilient-chat/chat-runtime.tsx#L328)）

主页用 `WorkflowChatTransport`，`api: '/api/chat'`，由 AI SDK 触发 POST。断线时通过 `prepareSendMessagesRequest` 切到 `GET /api/chat/{runId}/stream`，带 `x-page-resume: 1` 头。

**2. 后端 `/api/chat`**（[routes.ts#L867](file:///Users/keen/Desktop/code/projects/chat/apps/api/src/routes.ts#L867)）

跟通用 Agent API 最大的区别：**创建 Run 后不返回 202 + runId，而是直接把响应作为 SSE 流返回**——所以前端不需要"先 POST 拿 runId 再 GET 订阅"两步。处理顺序：

1. Zod 解析 `chatRequestSchema`，取出最后一条 `user` 消息文本
2. 附件按引用校验（必须是本人、已就绪、未被其他 run 占用）
3. `getOrCreateExternalSession`：新建会话同时分配独立 workspace 目录
4. 知识库兜底：未显式传 `knowledge_base_ids` 时自动检索用户可见的全部库（项目记忆里的硬约束）
5. `createRun`：在**同一 PostgreSQL 事务**里写 `agent_runs` + `run_dispatch_outbox`，保证 job 不丢
6. `outbox.wake()`：唤醒 Outbox Dispatcher 把任务投到 BullMQ
7. `streamWorkflowRun(...)`：把当前 HTTP 响应升级为 SSE 流

**3. SSE 实现**（[sse.ts#L25](file:///Users/keen/Desktop/code/projects/chat/apps/api/src/sse.ts#L25)）

关键设计：**SSE 不直接消费 Redis 消息**。Redis Pub/Sub 只负责"通知有新事件"，真正的事件内容从 PostgreSQL `run_events` 表按 `seq > cursor` 读取。这样：

- 前端晚连 SSE 不会漏事件（先从 PG 补发已产生的）
- 断线重连时浏览器自动带 `Last-Event-ID`，服务端从对应 seq 之后继续补发
- Run 完成/失败/取消后服务端关闭 SSE

**4. Worker 侧**（apps/worker）

消费 BullMQ Job → 拿 session 分布式锁 → 创建/连接沙箱 → 跑 agent-core。每产出一个事件就 `persistEvent`（写 PG + 发 Redis 通知），所以 API 侧 SSE 才能按 seq 拉取。

## 跟通用 Agent API 的对照

| 项 | 主页 `/api/chat` | 通用 Agent API |
|---|---|---|
| 创建 | `POST /api/chat` | `POST /api/agent/sessions/:id/runs` |
| 响应 | **直接 SSE 流**（200） | 202 + `{ id, status }` |
| 订阅 | 同一连接续流 | `GET /api/agent/runs/:id/events` |
| 断线恢复 | `GET /api/chat/:runId/stream` | `GET /api/agent/runs/:id/events`（带 Last-Event-ID）|
| 附件 | 内联 `attachment_ids` | 不带 |

简单说：主页选择"一步到位"是为了让 AI SDK 的 `useChat` 能直接接 SSE 流，少一次往返；断线时再用 `/stream` 这条专用恢复通道补齐。底层 Run 创建、Outbox、BullMQ、`run_events` + Redis Pub/Sub 这套基础设施两条链路是共享的。


### 关于刷新重放
有保存，但要区分两种 cursor：

- 主聊天 SSE：前端会统计已收到的完整 `data:` 帧数，保存为 `chunkIndex`。存储位置是 [persistence.ts](/Users/keen/Desktop/code/projects/chat/apps/web/app/lib/persistence.ts:49)，key 为：

  ```text
  resilient-chat:last-run:${userId}
  ```

  内容包含 `chatId`、`runId`、`chunkIndex`、`messages`、`pending`。

- 每收到完整 SSE 帧，都会更新 `localStorage`，见 [events.ts](/Users/keen/Desktop/code/projects/chat/apps/web/app/components/resilient-chat/events.ts:246)。

不过有个关键点：页面刷新后的恢复请求目前带的是 `x-page-resume: 1`，见 [chat-runtime.tsx](/Users/keen/Desktop/code/projects/chat/apps/web/app/components/resilient-chat/chat-runtime.tsx:347)。服务端因此从 `0` 开始全量重放，而没有直接使用 localStorage 里的 `chunkIndex` 精确续传。

另外，`/api/agent/runs/:runId/events` 会推标准 SSE `id: runId:seq`；但主聊天前端走的是 `/api/chat/:runId/stream`，保存的是自己统计的 `chunkIndex`，不是服务端事件的 `seq cursor`。


### 当前 Web 主聊天没有使用 `/api/agent/sessions/:sessionId/runs`和`/api/agent/runs/:runId/events`。  
它们目前只出现在：

- API 路由本身
- 文档
- `curl` 验收流程
- SSE 可观测性测试

没有实际前端调用方。

它们的定位是“通用/headless Agent API”：

```text
POST /api/agent/sessions/:sessionId/runs
        ↓ 返回 202 + runId
GET  /api/agent/runs/:runId/events
        ↓ 订阅原始 AgentEvent
```

这套接口适合：

- 非 AI SDK 客户端
- CLI、移动端或第三方系统集成
- 只关心工具、审批、Todo 等原始事件的消费者
- 使用标准 `EventSource + Last-Event-ID`
- 不希望绑定 `UIMessageChunk` 协议的客户端

而主页使用的是专门的 AI SDK 适配接口：

```text
POST /api/chat
        ↓ 创建 run 并直接返回 UIMessageChunk SSE

GET /api/chat/:runId/stream
        ↓ 重放 UIMessageChunk
```

所以整体分层是：

```text
run_events / AgentEvent        ← 平台原始协议
          ├─ /agent/.../events ← 通用客户端
          └─ /chat/.../stream  ← 转换成 AI SDK UIMessageChunk
```

结论是：

- 从架构定位看，`/events` 是为了保留一个不绑定 AI SDK 的通用 Agent API。
- 从当前实际使用看，它确实没有正式客户端，属于预留的平台能力。
- 如果这个项目永远只服务当前 AI SDK Web UI，也不开放 API，那么这个 endpoint 可以删除以减少维护面。
- 如果未来可能接 CLI、App、自动化系统或开放平台，保留原始事件接口是合理的；`UIMessageChunk` 应该只是展示层协议，不适合作为平台唯一协议。
